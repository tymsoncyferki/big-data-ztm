\section{Datasources}
Data used in the project will be obtained from data published by the city of Warsaw through its open data APIs, available at
(\texttt{https://dane.um.warszawa.pl}), but with multiple endpoints of both streaming and batch nature. Polled data is returned in json format for all endpoints available. All data size estimations where aquired using models available in Gemini free tier.
\subsection{Streaming data}
\begin{itemize}

  \item \textbf{Vehicle position data} - live GPS
    pings for every active vehicle: \texttt{Lat}, \texttt{Lon}, \texttt{Time},
    \texttt{Lines}, texttt{Brigade}, \texttt{VehicleNumber}. During rush hour there are about 450 trams and 1400 buses deployed, and such information is refreshed every 10s, though we would probably poll it in larger intervals, in order not to overload our limited infrastructure and not to exceed potential rate-limiting. A result of single poll has estimated size of 200KB.
  \item \textbf{Weather data} - air and surface temperature,
    precipitation,humidity, wind, and visibility for 18 stations located throughout the city. This data is refreshed every 10 minutes, though in order to use it as a streaming data source it is possible to poll it in shorter intervals for this puprose. A result of a single poll is estimated size of 4KB.
     \item \textbf{Air quality data} - returns a json with short description, monitoring station parameters, including type and location, and air quality parameters in form of nested records for 108 stations located throughout the city. This data is refreshed every 10 minutes, though in order to use it as a streaming data source it is possible to poll it in shorter intervals for this puprose. A result of a single poll is estimated size of 120KB.
\end{itemize}
\subsection{Batch data}
\begin{itemize}
  \item  \textbf{Timetable data} (static data, which should be acquired once per day) -
    stop locations, line-stop assignments, and per-brigade precise schedules
    for every  stop-line-brigade combination in the network. This data daily (assuming daily batches) estimated size is at 140-200MB.
\end{itemize}

\section{Data Processing Steps}

The proposed solution is based on the \textbf{Lambda Architecture}, which combines the processing of current observations with the analysis of historical data. These two paths support real-time delay predictions and historical statistics, respectively. Their results are brought together in a serving layer and displayed through a dashboard. Figure~\ref{fig:lambda-data-flow} presents the overall data flow.

    \centering
    \includegraphics[width=\linewidth,height=0.8\textheight,keepaspectratio]{lambda_data_flow.png}
    \caption{High-level data flow for stream and batch processing.}
    \label{fig:lambda-data-flow}
\end{figure}

\subsection{Data ingestion}

The system will collect three types of stream data: vehicle GPS positions, weather measurements, and air quality measurements. Public transport timetables will form a separate batch source, refreshed approximately once per day. The ingestion component will retrieve and validate data from the corresponding APIs. Original responses from all four sources will be archived in HDFS, while incoming GPS and environmental observations will also be forwarded to Kafka for stream processing.

\subsection{Batch processing}

The batch path will use the historical data stored in HDFS. Processing will produce three groups of datasets: \textbf{Raw}, containing the original source records; \textbf{Cleaned}, containing standardised and validated data; and \textbf{Processed}, containing integrated data and analytical results. The cleaned and processed datasets will be stored in Parquet format.

Historical GPS observations will be combined with timetables and environmental measurements to estimate delays and prepare features for machine learning. The batch path will also calculate statistics such as average delays by line, stop, and time period. These datasets will remain available in HDFS, while selected aggregates will be transferred to the serving layer.

A prediction model will be trained and evaluated using the processed historical data. The resulting model will be saved in HDFS for use by the stream path. The batch path will also make the latest processed timetable available for real-time calculations.

\subsection{Stream processing}

The stream path will continuously receive GPS, weather, and air quality events from Kafka. Current vehicle observations will be combined with the latest environmental information and the processed timetable to determine the current transport situation. The stream processor will then prepare input features and use the previously trained model to predict delays.

The resulting vehicle positions, environmental measurements, estimated delays, predictions, and current statistics will be written to Cassandra. This provides the serving layer with regularly updated information about public transport conditions.

\subsection{Data consumption}

The dashboard will combine current information from the stream path with historical aggregates generated by the batch path. Users will be able to view vehicle positions, environmental conditions, historical delay patterns, and delay predictions in one application.

The system will use open-source Big Data technologies organised into ingestion, batch, speed, serving, and consumption components. Figure~\ref{fig:lambda-infrastructure} shows the proposed technologies and their main connections.

\end{figure}

\subsection{Ingestion infrastructure}

\textbf{Apache NiFi} will coordinate data collection from the external APIs. It will store raw copies of the collected observations and timetables in HDFS for historical processing, while forwarding live observations to \textbf{Apache Kafka}. Kafka will provide separate topics for GPS, weather, and air quality data.

\subsection{Batch layer infrastructure}

\textbf{Hadoop HDFS} will be the main historical storage system, holding Raw, Cleaned, and Processed datasets, timetable snapshots, and trained models. \textbf{Apache Spark} will perform batch transformations, source integration, and aggregation. \textbf{Hive Metastore} will store table definitions for the cleaned and processed files in HDFS, allowing Spark SQL to access the datasets as structured tables.

\textbf{Spark MLlib} will be used to train and evaluate the prediction model using historical features prepared by Spark. The trained model will be stored in HDFS and made available to the speed layer.

\subsection{Speed layer infrastructure}

\textbf{Spark Structured Streaming} will consume events from Kafka and process current observations. It will enrich them with the timetable prepared by the batch layer, calculate current features, and generate predictions using the saved \textbf{Spark MLlib} model. The predictions and other current results will be written to Cassandra.

\subsection{Serving and dashboard infrastructure}

\textbf{Apache Cassandra} will store current data and predictions from the speed layer together with selected historical aggregates from the batch layer. \textbf{Streamlit} will provide the interactive dashboard and retrieve the information needed for its visualisations from Cassandra.

\subsection{Deployment}

The initial solution will be deployed using \textbf{Docker Compose}, with the main technologies running as containerised services. This arrangement will simplify development and integration of the individual project components.
